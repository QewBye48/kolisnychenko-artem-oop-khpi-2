# Звіт до лабораторної роботи №6

## Тема роботи

Поліморфізм з абстрактними класами в Java.

## Варіант

Варіант 5 — способи доставки.

## Мета роботи

Метою лабораторної роботи є отримання практичних навичок створення поліморфних моделей у Java з використанням абстрактних класів.

У роботі потрібно показати використання абстрактного базового класу, спільного стану, абстрактного методу, перевизначення методів у підкласах та поліморфного виклику через базовий тип.

---

## 1. Опис предметної області

У даній лабораторній роботі розглядається предметна область способів доставки.

У системі можуть існувати різні способи доставки замовлення:

- кур'єрська доставка;
- доставка до поштомата;
- доставка дроном.

Усі ці способи доставки мають спільні дані: номер замовлення, адресу доставки та базову вартість. Але кінцева вартість доставки для кожного типу розраховується по-різному.

Тому для цієї задачі доречно використати абстрактний клас `DeliveryMethod`, а конкретні способи доставки реалізувати як його підкласи.

---

## 2. Побудована ієрархія класів

У роботі було створено таку ієрархію:

```text
DeliveryMethod
├── CourierDelivery
├── ParcelLockerDelivery
└── DroneDelivery
```

Клас `DeliveryMethod` є абстрактним базовим класом.

Класи `CourierDelivery`, `ParcelLockerDelivery` і `DroneDelivery` є конкретними підкласами.

---

## 3. Обґрунтування абстрактного базового класу

Абстрактний клас `DeliveryMethod` є семантично коректним, тому що він описує загальне поняття способу доставки.

Сам по собі об'єкт `DeliveryMethod` створювати недоцільно, тому що це занадто загальне поняття. У реальній програмі завжди використовується конкретний спосіб доставки: кур'єром, через поштомат або дроном.

Тому `DeliveryMethod` зроблено абстрактним класом. Він містить спільний стан і спільну поведінку, а конкретні підкласи реалізують власний спосіб розрахунку вартості.

---

## 4. Спільний стан і спільна поведінка

До абстрактного класу `DeliveryMethod` було перенесено спільний стан, який є у всіх способів доставки:

- `orderId` — номер замовлення;
- `address` — адреса доставки;
- `basePrice` — базова вартість доставки.

Також у базовому класі реалізовано спільні методи:

- `getOrderId()`;
- `getAddress()`;
- `getBasePrice()`;
- `getInfo()`.

Метод `getInfo()` повертає коротку інформацію про доставку. У підкласах він може перевизначатися, щоб додати специфічні дані конкретного способу доставки.

---

## 5. Поліморфний контракт

Основним поліморфним методом у роботі є:

```text
calculatePrice()
```

У базовому класі він оголошений як абстрактний:

```java
public abstract double calculatePrice();
```

Цей метод визначає спільний контракт для всіх способів доставки: кожен тип доставки повинен уміти розраховувати кінцеву вартість.

Кожен конкретний підклас реалізує цей метод по-своєму.

---

## 6. Спеціалізація підкласів

### 6.1 Клас `CourierDelivery`

Клас `CourierDelivery` описує кур'єрську доставку.

Власне поле класу:

- `distanceKm` — відстань доставки в кілометрах.

Метод `calculatePrice()` розраховує вартість з урахуванням відстані:

```text
basePrice + distanceKm * 10
```

Тобто чим більша відстань доставки, тим більшою буде кінцева ціна.

### 6.2 Клас `ParcelLockerDelivery`

Клас `ParcelLockerDelivery` описує доставку до поштомата.

Власне поле класу:

- `lockerNumber` — номер поштомата.

Метод `calculatePrice()` додає фіксовану доплату до базової вартості:

```text
basePrice + 20
```

Цей спосіб доставки не залежить від відстані або ваги в даній спрощеній моделі.

### 6.3 Клас `DroneDelivery`

Клас `DroneDelivery` описує доставку дроном.

Власне поле класу:

- `weightKg` — вага посилки.

Метод `calculatePrice()` розраховує вартість з урахуванням ваги:

```text
basePrice + weightKg * 30
```

Тобто чим більша вага посилки, тим більшою буде вартість доставки.

---

## 7. Використання `@Override`

У кожному конкретному підкласі метод `calculatePrice()` перевизначено за допомогою анотації `@Override`.

Також у підкласах перевизначено метод `getInfo()`, щоб додати до загальної інформації власні дані:

- у `CourierDelivery` додається відстань;
- у `ParcelLockerDelivery` додається номер поштомата;
- у `DroneDelivery` додається вага посилки.

Це показує, що підкласи не просто наслідують базовий клас, а спеціалізують його поведінку.

---

## 8. Поліморфізм у клієнтському коді

Поліморфізм продемонстровано у класі `Main`.

У програмі створюється масив базового типу:

```java
DeliveryMethod[] deliveries = {
    new CourierDelivery("ORD-001", "Харків, вул. Сумська, 20", 100, 5),
    new ParcelLockerDelivery("ORD-002", "Харків, проспект Науки, 10", 80, "A-15"),
    new DroneDelivery("ORD-003", "Харків, вул. Кирпичова, 2", 150, 2.5)
};
```

У цьому масиві зберігаються об'єкти різних конкретних класів, але всі вони мають спільний тип `DeliveryMethod`.

Далі в циклі викликаються методи:

```java
for (DeliveryMethod delivery : deliveries) {
    System.out.println(delivery.getInfo());
    System.out.println("Price: " + delivery.calculatePrice());
}
```

Це і є поліморфний виклик. Змінна `delivery` має тип `DeliveryMethod`, але Java під час виконання викликає метод `calculatePrice()` саме того класу, об'єкт якого реально знаходиться в масиві.

Для `CourierDelivery` виконується розрахунок за відстанню, для `ParcelLockerDelivery` — фіксована доплата, а для `DroneDelivery` — розрахунок за вагою.

## 12. Додаткове завдання: аналіз моделі з ЛР2

У лабораторній роботі №2 використовувалась модель спортивного клубу.

У ній були такі класи:

- `SportsClub`;
- `Student`;
- `Coach`;
- `SportSection`;
- `Schedule`;
- `Enrollment`.

Клас `SportsClub` містив списки секцій, студентів та записів на секції, тобто виконував роль головного контейнера системи. :contentReference[oaicite:1]{index=1}

Клас `Coach` мав поля `fullName` і `sportType`, тобто описував тренера та вид спорту, з яким він працює. :contentReference[oaicite:2]{index=2}

У цій моделі можна спробувати ввести поліморфну абстракцію для сутностей, які описують людей. Наприклад, `Student` і `Coach` можна розглядати як спеціалізовані форми одного узагальненого типу `Person`.

Можлива ієрархія:

```text
Person
├── Student
└── Coach
```

Абстрактний клас `Person` міг би містити спільний стан:

- `fullName`.

Також у ньому можна було б оголосити абстрактний метод:

```java
public abstract String getRoleInfo();
```

Клас `Student` реалізував би цей метод як інформацію про студента, а клас `Coach` — як інформацію про тренера.

При цьому класи `SportsClub`, `SportSection`, `Schedule` і `Enrollment` не слід включати до цієї ієрархії, тому що вони не є різновидами людини. Вони мають інші ролі в системі та краще моделюються через асоціацію, агрегацію або композицію.

Отже, у моделі з ЛР2 коректна поліморфна абстракція можлива для класів `Student` і `Coach`, але не для всіх сутностей системи.

## 13. Висновок

У ході виконання лабораторної роботи було створено поліморфну модель для варіанта 5 — способи доставки.

У програмі реалізовано абстрактний клас `DeliveryMethod`, який містить спільний стан і спільну поведінку для всіх способів доставки.

Було створено три конкретні підкласи:

- `CourierDelivery`;
- `ParcelLockerDelivery`;
- `DroneDelivery`.

Кожен підклас перевизначає метод `calculatePrice()` і реалізує власний спосіб розрахунку вартості доставки.

У класі `Main` було продемонстровано реальний поліморфний виклик через базовий тип `DeliveryMethod`.

Також було створено UML-діаграму та тести для перевірки роботи класів.

Додатково було проаналізовано модель з лабораторної роботи №2 і зроблено висновок, що в ній можна коректно ввести абстрактний базовий клас `Person` для класів `Student` і `Coach`.

Отже, лабораторна робота показала різницю між простим успадкуванням і поліморфізмом: у поліморфній моделі клієнтський код працює через один базовий тип, а конкретна поведінка визначається фактичним типом об'єкта під час виконання програми.
