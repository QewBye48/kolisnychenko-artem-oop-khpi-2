# Вимоги до програми
## Варіант 5 — Засоби командної роботи над проєктами

## Загальні вимоги

1. Програма повинна реалізовувати просту модель засобів командної роботи над проєктами.
2. Програма повинна бути написана мовою Java.
3. Програма повинна використовувати принципи об'єктно-орієнтованого програмування.
4. У програмі повинні бути використані інтерфейси як поведінкові контракти.
5. Програма повинна демонструвати множинну реалізацію інтерфейсів.
6. Програма повинна працювати у консольному режимі.

---

## Функціональні вимоги

1. Система повинна містити об'єкти, які використовуються під час командної роботи над проєктом.
2. У програмі повинні бути реалізовані такі сутності:
    - картка завдання;
    - звіт про помилку;
    - примітка до рев'ю.
3. Частину об'єктів можна призначати виконавцю.
4. Частину об'єктів можна коментувати.
5. Один або кілька об'єктів повинні підтримувати обидві можливості:
    - призначення виконавцю;
    - додавання коментаря.
6. Програма повинна виводити інформацію про виконання дій у консоль.
7. Програма повинна демонструвати роботу з об'єктами через типи інтерфейсів.

---

## Вимоги до структури

1. Програма повинна містити щонайменше два інтерфейси:
    - `Assignable`;
    - `Commentable`.

2. Інтерфейс `Assignable` повинен описувати можливість призначення об'єкта виконавцю.

3. Інтерфейс `Commentable` повинен описувати можливість додавання коментаря до об'єкта.

4. Програма повинна містити щонайменше три конкретні класи:
    - `TaskCard`;
    - `BugReport`;
    - `ReviewNote`.

5. Клас `TaskCard` повинен реалізовувати інтерфейси:
    - `Assignable`;
    - `Commentable`.

6. Клас `BugReport` повинен реалізовувати інтерфейси:
    - `Assignable`;
    - `Commentable`.

7. Клас `ReviewNote` повинен реалізовувати інтерфейс:
    - `Commentable`.

8. Усі методи, які реалізуються з інтерфейсів, повинні бути позначені анотацією `@Override`.

## Вимоги до інтерфейсів

### `Assignable`

Інтерфейс повинен містити методи:

```java
String assignTo(String personName);

String getAssignee();
```

### `Commentable`

Інтерфейс повинен містити методи:

```java
String addComment(String comment);

int getCommentsCount();
```

---

## Вимоги до класів

### `TaskCard`

Клас описує картку завдання.

Поля:

- `title` — назва завдання;
- `description` — опис завдання;
- `assignee` — виконавець;
- `commentsCount` — кількість коментарів.

Клас повинен реалізовувати:

- `Assignable`;
- `Commentable`.

---

### `BugReport`

Клас описує звіт про помилку.

Поля:

- `bugId` — номер помилки;
- `severity` — рівень важливості;
- `assignee` — відповідальний виконавець;
- `commentsCount` — кількість коментарів.

Клас повинен реалізовувати:

- `Assignable`;
- `Commentable`.

---

### `ReviewNote`

Клас описує примітку до рев'ю.

Поля:

- `author` — автор примітки;
- `text` — текст примітки;
- `commentsCount` — кількість коментарів.

Клас повинен реалізовувати:

- `Commentable`.

---

## Вимоги до демонстрації в `Main`

1. У класі `Main` потрібно створити об'єкти:
    - `TaskCard`;
    - `BugReport`;
    - `ReviewNote`.

2. Потрібно створити масив типу `Assignable[]`:

```java
Assignable[] assignableItems = {
    task,
    bug
};
```

3. Через масив `Assignable[]` потрібно викликати метод:

```java
assignTo(){
}
```

4. Потрібно створити масив типу `Commentable[]`:

```java
Commentable[] commentableItems = {
    task,
    bug,
    note
};
```

5. Через масив `Commentable[]` потрібно викликати метод:

```java
addComment(){
}
```

6. Потрібно показати один об'єкт через два різні інтерфейсні посилання:

```java
Assignable assignableView = task;
Commentable commentableView = task;
```

## Вимоги до тестування

1. Тести повинні бути написані з використанням JUnit Jupiter.
2. Тести повинні перевіряти контракт інтерфейсу `Assignable`.
3. Тести повинні перевіряти контракт інтерфейсу `Commentable`.
4. Тести повинні перевіряти клас `TaskCard`.
5. Тести повинні перевіряти клас `BugReport`.
6. Тести повинні перевіряти клас `ReviewNote`.
7. Тести повинні підтверджувати, що один клас може використовуватися через два різні інтерфейси.

---

## Нефункціональні вимоги

1. Код повинен бути простим і зрозумілим.
2. Назви класів, методів і змінних повинні відповідати їхньому призначенню.
3. Програма повинна мати зрозумілий консольний вивід.
4. Проєкт повинен містити файл `pom.xml`.
5. Проєкт повинен містити файл `README.md`.
6. Проєкт повинен містити файл `REPORT.md`.
7. Проєкт повинен містити UML-діаграму у форматі PlantUML або PNG/PDF.

---

## Обмеження

1. Не потрібно будувати штучну ієрархію успадкування класів.
2. Інтерфейси повинні описувати саме поведінкові ролі.
3. Не можна створювати інтерфейси, які просто дублюють один конкретний клас.
4. Клієнтський код не повинен працювати тільки з конкретними класами.
5. У програмі обов'язково має бути робота через типи інтерфейсів.

---

## Очікуваний результат

Після запуску програма повинна вивести результат призначення виконавців, додавання коментарів і приклад використання одного об'єкта через два різні інтерфейси.

Приклад виводу:

```text
=== Обробка об'єктів через інтерфейс Assignable ===
Завдання "Створити сторінку входу" призначено виконавцю: Колісниченко Артем
Помилку BUG-101 призначено виконавцю: Колісниченко Артем

=== Обробка об'єктів через інтерфейс Commentable ===
Коментар додано до завдання "Створити сторінку входу": Перевірено куратором проєкту
Коментар додано до помилки BUG-101: Перевірено куратором проєкту
Коментар додано до примітки від Артем: Перевірено куратором проєкту
```
